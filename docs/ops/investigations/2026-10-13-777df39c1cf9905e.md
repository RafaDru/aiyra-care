## Resumo

Incidente automático do piloto **client error → CH**: falha no fluxo **Configurações → Conta → Excluir conta** (`DELETE /auth/account`). O fingerprint confirma ingest com código estável `account_delete_failed` (feature `account_settings`), típico do handler em `DeleteAccountCard` quando o cliente **não** extrai status HTTP da exceção.

## Hipóteses (ranqueadas)

1. **`DELETE /auth/account` retornou 5xx** — Em `api.request`, respostas 5xx JSON disparam mensagem de playbook **sem** substring `HTTP NNN`; `httpStatusFromError` falha e `reportAccountSettingsFailure('account_delete', …)` grava `account_delete_failed` (fingerprint `777df39c1cf9905e`). Causa provável no servidor: rollback em `AccountDeletionService` (FK/cascade PG, conta inexistente, erro em transação ao apagar pacientes/`app_accounts`).
2. **4xx de negócio (400 confirmação, 401 sessão)** — Erros via `ApiResponseError` também não passam por `httpStatusFromError` (só regex na mensagem); o mesmo fingerprint `account_delete_failed` mascara 400/401. Menos provável se o usuário digitou `EXCLUIR` autenticado, mas vale confirmar status no bundle/`client_errors`.
3. **Resposta não-JSON / proxy (HTML 404)** — Mensagens como «API indisponível ou rota não encontrada» geram o mesmo código agregado `account_delete_failed`. Em `integration` com API em `127.0.0.1:3010`, desalinhamento web↔API ou rota ausente no deploy local é possível; suite QA cita HTTP 404 quando `DELETE` não existe ou proxy omite `auth`.
